## What it is

An internal harness that runs Mercury's real system prompt, real tools, and real context-primer wiki injection against several local Ollama models, to compare how reliably each one calls tools. Only the Jira CLI subprocess is mocked (`fixtures.ts`); everything else is the same code that runs in production.

## Setting the models

`BENCH_MODELS` is the only source, there's no checked-in default roster. It's a JSON array of `{tag, family, activeParamsB}`, validated by `load-models.ts` (`.strict()`, matching `src/tools/cli-config-schema.ts`'s convention: a typo'd field fails loudly instead of getting silently dropped). Leaving it unset is a startup error, not an implicit "run everything":

```bash
export BENCH_MODELS='[
  { "tag": "qwen3.8:27b", "family": "dense", "activeParamsB": 27 },
  { "tag": "muse-glimmer:30b", "family": "dense", "activeParamsB": 30 },
  { "tag": "gemma4:31b", "family": "dense", "activeParamsB": 31 }
]'
```

`family` is `"dense"` or `"moe"`. Both fields feed straight into `results/analysis/stats.md`'s per-model breakdown, so an ad-hoc one-off model still needs real values, not a placeholder.

## Running it

Pull the models in Ollama first, then:

```bash
bun run benchmark/run.ts
```

Config goes through env vars, not argv, matching the rest of the codebase:

| Var | Default | What it does |
|---|---|---|
| `BENCH_PROMPT` | `baseline.md` | System prompt file, under `prompts/` |
| `BENCH_MODELS` | none, required | See [Setting the models](#setting-the-models) |
| `BENCH_TRIALS` | `15` | Trials per (model, test case) |
| `OLLAMA_HOST` | `http://localhost:11434` | Same var the rest of Mercury uses |

The run loops model × test case × trial × round, and writes one JSON file per round straight to `results/`. Re-running overwrites the same trial/round's file in place, there's no versioning inside `results/` itself.

## Reading the results

### Trial files

`results/<model>/<testCase>/trial-<N>.json` for a single-turn test case, or `trial-<N>-round-<M>.json` per live turn for a multi-turn one (`pressure`, currently). Each file is self-contained: model metadata, the exact messages sent for that round, the tool-call steps, the model's final text, and a mechanical `derived.outcome` (`real-tool-call` / `hallucinated` / `no-attempt` / `error`).

That classification is mechanical, not a verdict. The harness doesn't judge whether an answer was actually correct, reading the results for real is a separate, manual step.

### Aggregate reports

```bash
bun run benchmark/analyze-stats.ts
bun run benchmark/analyze-tool-sequences.ts
```

Both scan every trial file under `results/` and write to `results/analysis/`: `stats.md` (aggregate rates, each table labeled with its own denominator) and `tool-sequences.md` (the ordered tool-call sequence for every single trial). `summary.md` in the same folder isn't generated by either script, it's a synthesis someone writes by hand after reading the other two.

### The archive zip

At the end of every run, `archive-results.ts` zips the whole `results/` dir into `results-<model-tags>-<unixtime>.zip` next to itself, model tags joined by `+` so you can see the roster a given zip covers without unzipping it. `results/` itself is left untouched, so the analysis scripts above keep reading the latest run with no path changes. The zip is gitignored, a local backup to fall back on if you want to compare against an older run later.

## Known limitations

- If a model ever calls `write_file`, it writes for real into `fixture-vault/`, a real filesystem vault, not mocked. Run `git status`/`git checkout fixture-vault/` there after a run if a trial's output looks contaminated by a prior trial's write.
- `recall_tool_calls` is in the real tool set for prompt fidelity, but nothing in this harness ever calls `recordStep`, so it always returns an empty log here. A model that calls it gets a structurally correct but empty answer, not an error.
