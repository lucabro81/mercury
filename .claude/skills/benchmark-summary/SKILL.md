## Why this exists

`benchmark/results/analysis/summary.md` is the narrative synthesis a reader actually opens first — `stats.md` and `tool-sequences.md` are raw aggregate tables and per-trial logs, not something to read cold. Per `benchmark/README.md`'s own words, summary.md "isn't generated by either script, it's a synthesis someone writes by hand after reading the other two." This skill is that "someone" — it doesn't replace `stats.md`/`tool-sequences.md`, it reads them and writes the synthesis.

## Preconditions — do nothing if these aren't met

1. `benchmark/results/analysis/stats.md` and `benchmark/results/analysis/tool-sequences.md` must both already exist. This skill never runs `analyze-stats.ts`/`analyze-tool-sequences.ts` itself — if either file is missing, stop and tell the user to run them (or the benchmark itself, if `results/` has no trial data at all) first. Don't generate a summary from data you didn't verify is there.
2. If `benchmark/results/analysis/summary.md` already exists, don't silently overwrite it: tell the user it already exists and ask whether to overwrite before doing anything else. If it doesn't exist yet, just write it directly, no confirmation needed — that's the normal case (a fresh benchmark run, followed by the two analyze scripts, followed by this skill).

## Steps

1. Read `benchmark/results/analysis/stats.md` in full — every table, every heading, every denominator note. Skim `benchmark/results/analysis/tool-sequences.md` for concrete examples worth quoting (a specific trial that illustrates a pattern the aggregate numbers alone don't explain — e.g. a model that technically failed a metric for a defensible reason visible only in its actual tool-call sequence).
2. Write `benchmark/results/analysis/summary.md` with this structure (a template for shape, not for content — see the warning below):
   - **`# Sintesi del benchmark tool-calling`**
   - **`## Cos'è`** — what this run covers: how many models, scenarios, trials, a one-line pointer to `stats.md`/`tool-sequences.md`.
   - **`## Come si legge`** — a glossary: what each test case in `run.ts`'s `TEST_CASES` is actually testing, what each `outcome` value means, and for every table that's actually in `stats.md` today, what its own denominator is (copy each table's own labeled denominator line, don't reinterpret it).
   - **`## Modelli osservati`** — one `###` subsection per model actually present in this run's data, a short prose paragraph with concrete numbers pulled from `stats.md`, calling out what's notable (a weakness, a standout strength, a surprising tradeoff) rather than restating every cell of every table.
   - **`## File completi`** — links to `stats.md` and `tool-sequences.md`.
3. **Don't copy wording from a previous summary.md**, even as a starting point — only use it (if it exists and you're regenerating after confirmation) to sanity-check the shape/tone, never for factual claims. The tables in `stats.md` change over time (they did, in the same session that created this skill — a table got renamed and a metric was dropped); a synthesis is only correct if every claim in it traces back to the current `stats.md`/`tool-sequences.md` you just read, not to what an older summary said about an earlier run.

## When to stop and ask instead of guessing

- `stats.md` or `tool-sequences.md` is missing — say so, don't fabricate a summary from memory of a previous run.
- `summary.md` already exists — ask before overwriting, per the precondition above.
- A table's data looks inconsistent with the roster (e.g. a model listed with zero trials, or a denominator column that's always "—") — flag it in the summary itself, or ask the user, rather than writing around it silently.
